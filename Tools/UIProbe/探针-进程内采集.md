## 一、`frame-pacer` —— vsync 分母（两把仪器同窗各测一遍）

**是什么**：同一个墙钟窗口里同时跑 CVDisplayLink（合成器高优先级线程）与 CADisplayLink（主 runloop），
各自给出相邻 vsync 间隔的分布，并显式回答「两者是否一致」。
**怎么调**：

```bash
xcrun swiftc -O Tools/UIProbe/frame-pacer.swift -o tmp/uiprobe/frame-pacer
tmp/uiprobe/frame-pacer --seconds 30 --out tmp/uiprobe/pacer-30s.csv
```

**口径**（写死在文件头注释里）：`vsync_n` = 回调次数（间隔个数 = `vsync_intervals` = n−1）；
分位数走**相邻间隔**排序后的最近秩，函数与已提交的 `probe-vsync.swift` 逐字一致（尺子不许有两把）；
`vsync_skipped` = 间隔 > 1.5×本窗 P50 的次数；`instruments_agree=yes` 的条件是
**|ΔP50| ≤ 0.05 ms 且两把仪器的 skipped 相等**。
两块输出的先后顺序 = 契约列顺序（6 个 `vsync_*` 在前、`instrument=` 在末），所以下游按 7 行一块读。

**定位**：静止显示器本来就该是稳的，本工具**给 A2 当分母**（`frame-baseline` 第 10 列 `vsync_ms`），它自己不构成判据。

### 1.2 短窗对照（3 s，load 12.26，两把仪器都干净）

```
vsync_n=370 … vsync_max_ms=8.333 vsync_skipped=0 instrument=cvdisplaylink
vsync_n=362 … vsync_max_ms=8.333 vsync_skipped=0 instrument=cadisplaylink
instruments_agree=yes   instruments_p50_delta_ms=0.000   instruments_skipped_delta=0
```

### 1.3 两把仪器一致吗？——**P50 一致，尾部不一致，而且不一致是可解释的**

* 两把仪器在**任何窗**里 P50 都是 8.333 ms（Δ=0.000 ms），`link.duration` 也直报 0.008333 s ⇒ 120 Hz。
  这与主会话在 `probe-vsync`（提交 `54450f3`）里量到的一致，我这边**独立复现**。
* 30 s 窗里 `cadisplaylink` 出现 40 次 skipped、max 26.893 ms、min 6.287 ms，而 `cvdisplaylink` 全窗 8.333 ms 不动。
  机理清楚：CADisplayLink 走主 runloop，回调会被 runloop 上别的东西推迟；CVDisplayLink 走自己的高优先级线程。
  ⇒ **本进程主线程一空，两把仪器的 P50 就重合；一旦主线程有竞争，只有 cadisplaylink 的尾部会抬。**
  这条正是 A2 需要的信息：`frame-window`（仪器二，呈现帧）与 `turn`（仪器三，主线程 turn）都会吃到同一份竞争。
* `load1_before/after` 由工具自己打（`getloadavg`），所以 CSV/stdout 与基线表的 29/30 列天然对齐。
* 结论建议：**`vsync_ms` 分母取 `instrument=cvdisplaylink` 那一块**；`cadisplaylink` 块留作
  「现代非 deprecated 通道在 macOS 上确实可用」的证据，并当作「主线程被堵时会怎样」的探针。

### 1.4 CSV 可被独立复算（不是只有我这个工具自己能算出这个数）

CSV 每行一个时间戳（`instrument,seq,clock_ns,host_ns`）。用一段与工具无关的 Python 只读 CSV 复算：

```
cvdisplaylink: n=3610 P50=8.333 P95=8.333 P99=8.333 min=8.333 max=8.333 skipped=0
cadisplaylink: n=3555 P50=8.333 P95=8.333 P99=13.529 min=6.287 max=26.893 skipped=40
```

与 stdout 逐位相同 ⇒ 分母不是「工具自说自话」。

### 1.5 编译期证据：CVDisplayLink 确实 deprecated，但确实可用

```
warning: 'CVDisplayLinkCreateWithCGDisplay' was deprecated in macOS 15.0:
use NSView.displayLink(target:selector:), NSWindow.displayLink(target:selector:), or NSScreen.displayLink(target:selector:)
```

同一批 warning 也覆盖 `CVDisplayLinkGetActualOutputVideoRefreshPeriod` / `GetNominalOutputVideoRefreshPeriod` / `CVDisplayLinkStart`。
运行时它们照常出 120 Hz 的稳定回调（上面 3610 个戳）⇒ 「deprecated 但仍可用」在本机成立。

## 二、`probe-footprint` —— F5 的内存口径

**是什么**：按 pid 读 `phys_footprint`，并给 RSS 与比值当对照列。
**怎么调**：

```bash
xcrun swiftc -O Tools/UIProbe/probe-footprint.swift -o tmp/uiprobe/probe-footprint
tmp/uiprobe/probe-footprint --pid 1234          # 进程存续期内可重复调
tmp/uiprobe/probe-footprint --verify-self       # 两条口径在同一进程上对表
```

**两条路取同一个内核账**（`footprint_source=` 里如实写明用了哪条）：

* A `task_info(TASK_VM_INFO).phys_footprint` ← 契约点名的口径。
* B `proc_pid_rusage(RUSAGE_INFO_V4).ri_phys_footprint` ← 同 UID 免权限，内核里是同一个 phys_footprint 计数器。

### 2.1 原样输出（load 12.12，swift-frontend 0）

```
$ tmp/uiprobe/probe-footprint --verify-self
pid=31915
footprint_taskinfo_mb=1.52
footprint_rusage_mb=1.52
two_paths_delta_kb=0.0
calibers_match=yes
phys_footprint_mb=1.52
footprint_source=task_info(TASK_VM_INFO).phys_footprint

$ sleep 300 &  →  MYPID=31831
$ tmp/uiprobe/probe-footprint --pid 31831          # stderr 第一行 + stdout 全部
task_for_pid(31831) 失败 kr=5 ((os/kern) failure) —— 非 root / 无 com.apple.private.task-god 权限，预期行为
pid=31831
proc_name=sleep
phys_footprint_mb=0.86
footprint_source=proc_pid_rusage(RUSAGE_INFO_V4).ri_phys_footprint
task_info_ok=no
rusage_ok=yes
rss_mb=1.16
rss_source=proc_pidinfo(PROC_PIDTASKINFO).pti_resident_size
footprint_ratio=1.345

$ ps -o pid=,rss= -p 31831
31831   1184                                       # 1184 KB = 1.16 MB，与上面 rss_mb 逐位吻合（独立仪器）

$ kill 31831; tmp/uiprobe/probe-footprint --pid 31831 ; echo rc=$?
pid 31831 不存在（ESRCH）⇒ 不打任何 key。0 是「量到且为零」，这里什么都没量到。
rc=3                                               # 一个 key 都没打，符合「不许拿 0 冒充读数」
```

### 2.2 三条可直接引用的结论

1. **A 与 B 是同一个数**：同一进程上 `two_paths_delta_kb=0.0`、`calibers_match=yes` ⇒ 非 root 场景退回 B 不改变 F5 口径。
   （等值性只在**自身进程**上验过；对别人的 pid 拿不到 A，所以无法在它身上二次验证 —— 见 §4。）
2. **读别的 pid 走不通 A**：`task_for_pid` 返回 `kr=5 (os/kern) failure`，本机非 root 无 entitlement 是预期行为，
   不是 bug；所以驱动脚本必须按 `footprint_source=` 记录实际口径，别假定是 A。
3. **footprint ≠ RSS，但比值随进程大小变**：这个 `sleep` 只有 0.86 MB footprint / 1.16 MB RSS，ratio=1.345。
   契约里「本机 RSS ≈ 2× footprint」是**AIObservatory 那种量级进程**上的观察值，
   在小进程上不成立 ⇒ ratio 只能当对照列，不能当校验规则用（F5 判据只认 `phys_footprint_mb`）。

## 三、MetricKit 三问（`probe-metrickit`）

**怎么调**：

```bash
xcrun swiftc -O Tools/UIProbe/probe-metrickit.swift -o tmp/uiprobe/probe-metrickit
tmp/uiprobe/probe-metrickit --seconds 300 --induce-hang 10      # 订阅后把主线程堵 10 s 钓 hang
```

### (a) 编译期是否存在 → **存在，下限 macOS 12.0**

SDK 头文件实测（`MacOSX26.5.sdk/…/MetricKit.framework/Headers/`）：

```
MXMetricManager.h:32   API_AVAILABLE(ios(13.0), macos(12.0)) API_UNAVAILABLE(tvos, watchos)   @interface MXMetricManager
MXMetricManager.h:126  - (void)didReceiveMetricPayloads:…            API_AVAILABLE(macos(10.15))
```

（`API_UNAVAILABLE` 只关 tvOS / watchOS，**没有关 macOS**。）

无 `#available` 守卫直接引用两个符号，本机默认部署目标下**编译通过**（rc=0）；

Swift 侧真实名字（编译器 fix-it 实测，别照抄 iOS 文档）：`MXMetricManager.shared`、`add(_:)`、`remove(_:)`、
`pastPayloads`、`pastDiagnosticPayloads`、`didReceive(_ metrics:)` / `didReceive(_ diagnostics:)`。

### (b) 运行期能否订阅成功 → **能，而且把系统守护拉起来了**

`/usr/libexec/metrickitd` 存在（136 KB）、`/System/Library/LaunchAgents/com.apple.metrickitd.plist` 存在、

`class_present=yes`、`hang_diagnostic_class_present=yes`、`manager_ok=yes`、`subscribe_ok=yes`、`add_removed_ok=yes`。

所以对本车道要的东西（F4 的 `hang_events_n` 在 20–60 s 判据窗内出数），MetricKit 现在**不能用**；
对「MetricKit 在 macOS 上是否根本不可用」，本车道**不下结论**。

**需要 IFR（接口变更请求）**：若要把 MetricKit 变成可用尺子，必须产品侧做两件事，本车道无权也无可做：

1. 在 App 生命周期内 `MXMetricManager.shared.add(subscriber)`（`AIObservatoryUI` / App 层，属他人目录）；
2. 把 payload 落到 `AIOBSERVATORY_DATA_DIR` 下的自有存储，这样跨天窗口才读得到历史 hang。
   在此之前，`hang_events_n` 只能继续走 `xctrace` / `spindump`（A2/A3 那条线）。

## 四、未覆盖条件清单（别把这些当成已证）

1. **ProMotion 降频窗没测**：本机 `maximumFramesPerSecond=120`，但静止显示器可能降到 60 Hz 以下；
   我没有覆盖「降到 60 Hz 时 `vsync_p50_ms` 变成 16.667」这一支。基线表第 10 列要求**每行重测**，别拿本文件的 8.333 复用。
2. **主线程真的忙时两把仪器的分化**只在「空转但机器有负载」的 30 s 窗里间接触发过（cadisplaylink skipped=40）。
   没有覆盖 AIObservatory 真实交互（滚动 / 切页）时的分化幅度 —— 那是 A2 的窗。
3. **未验证第二块显示器**：只用 `CGMainDisplayID()`。多屏 / 外接屏刷新率不同的场景未测。
4. **`task_for_pid` 路径没有 root 验证**：非 root 下恒 `kr=5`。以 root 或带 entitlement 的宿主跑时会走 A 路径，
   届时 `footprint_two_paths_delta_kb` 才会打出来，我没见过那个数（只在自身进程上见过 0.0）。
5. **MetricKit 的跨天窗（≥24 h）没跑**，也没查过任何 `~/Library` 下的历史 payload（那是 §0 授权边界外的目录，
   即便能区分结论也不该由本车道越界去读）。
6. **MetricKit 的 hang 阈值未标定**：`--induce-hang 10` 只是「堵主线程 10 s」，MXHangDiagnostic 到底以多长算 hang、
   在 macOS 上由谁判定，都没证据。
7. **`footprint_ratio` 在大进程上的值未测**：本窗只有 0.86 MB 的 `sleep`。「RSS ≈ 2× footprint」是契约/主会话在
   AIObservatory 量级进程上的观察值，我没在真实 App 上二次确认（不许启动 AIObservatory）。
8. **`vsync_skipped` 与产品掉帧不是一回事**：`vsync_skipped` 量的是**显示器节奏本身**有没有跳；
   产品掉帧要用 `frame-window` 的呈现间隔去比它，本工具不构成判据。
9. 三个工具的**并发安全性未压测**：同窗跑多个 `frame-pacer` 只是各自读同一块屏，没做过互扰测量。

## 五、交回总控的 BLOCKERS

1. **MetricKit 要产品侧插桩才有投递可言**（见 §3(c)）→ 需要 IFR，涉及 `Sources/AIObservatoryUI/**`（workbuddy 独占）
   与 App 层装配（总控冻结区）。本车道一行都没碰。
2. **F4 的 `hang_events_n` 在 60 s 窗内没有进程内来源**：要么继续用 `xctrace`/`spindump`（外部仪器、有 attach 成本），
   要么接受 `n/a`。需要总控定「F4 是否允许 n/a 行」。
3. **`vsync_ms` 分母取哪一把仪器要定标准**：本文件建议 `cvdisplaylink`（尾部最干净、与 `probe-vsync` 同尺子），
   代价是继续吃一条 deprecated API。契约 `frame-baseline.schema.md` 第 10 列目前只写「仪器一实测」没点名，
   是否要把「instrument=cvdisplaylink」写进契约，请总控决定（改列=契约变更）。
4. `probe-footprint` 对**别人的 pid** 只能走 `proc_pid_rusage`（非 root）。等值性我已用自身进程证过（Δ=0.0 KB），
   但如果基线表要求 `footprint_source` 必须是 `task_info(TASK_VM_INFO)` 字面值，则需要 root 宿主或 entitlement → 也请定标准。
