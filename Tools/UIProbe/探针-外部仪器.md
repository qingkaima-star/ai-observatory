# 探针：外部仪器（WS-Frames / A3）

> Owner: WS-Frames。这份只回答一个问题：**不许改产品代码时，哪几把进程外的尺子真的能用、
> 用它给的数能判到哪一步。** 每个「能 / 不能」后面都跟着**我自己这一轮跑出来的原样输出**
> （不是文档、不是头文件的说法）。
> 列定义在 `frame-baseline.schema.md`，命令行在 `frames-tools.contract.md`。
> 所有实测都带当窗 `uptime` 与 `pgrep -f swift-frontend | wc -l`；load ≥ 15 的窗口只报差值不报达标。
> 机器：macOS 26.5.2 (25F84)，15 核，屏 AG275UXM 1920x1080@2.0x maxRefresh=120。

## 0. 一页结论

| 仪器 | 命令 | 能不能用 | 实测分辨率下限 | 代价 | 能判到哪一步 |
|---|---|---|---|---|---|
| 一 `probe-vsync` / `frame-pacer`（进程内 CVDisplayLink + CADisplayLink） | 既有 | **能** | vsync 本身（8.333 ms，纹丝不动） | 几乎为零 | 只量**显示端的拍子**，量不到某个窗口出没出画面 |
| 二 `frame-window`（进程外 ScreenCaptureKit 按窗口） | `xcrun swiftc -O Tools/UIProbe/frame-window.swift -o tmp/uiprobe/frame-window` | **能采到帧**，但按窗口通道有 **≈60 内容帧/s 的天花板** | 呈现间隔 P50 下限 ≈ **16.5 ms**（同窗整屏通道 9.4 ms） | 1280x820 采 30 s：CPU 可忽略（不存像素），产物只有 CSV | 能判「**慢于 60 fps 的劣化**」；**判不了 F1（≤8.333 ms）** |
| 三 `turn-trace.sh`（进程外 xctrace，Animation Hitches 模板，非 root 无开发者模式） | `Tools/UIProbe/turn-trace.sh --pid P --seconds 20` | **能**（两档模板都录出包并解出真数） | 主线程 turn 到 1 ms 级 | **20 s 窗 → 1.1–1.7 GB 包 + 79–294 s 墙钟**，且把被观测方拖慢 ≈1/3 | F4 可判（附口径折扣） |
| 三降档 `spindump` | `/usr/sbin/spindump …` | **不能**（要 root，`sudo -n` 要密码） | — | — | 只能作 note，不许进判据 |
| 旁证 `sample` | `sample P 3 -file tmp/frames/x.txt` | **能**（非 root） | 统计画像，非逐回合 | 轻 | 判「忙 vs 等」，**不进 F4 判据窗** |

**两条会被这份文件救回来的结论**：

1. 「SCStream 只为内容变化出帧」**在本机不成立** ⇒ 拿到达间隔当帧率会系统性虚报流畅（§1.4）。
2. 「xctrace 类 trace 在本机结构性不可得」**不成立** ⇒ F4 有外部通道（§2）。

## 1. 仪器二 `frame-window`（`Tools/UIProbe/frame-window.swift`）

### 1.1 交来的草稿有 4 个编译错，先原样复现

```
$ xcrun swiftc -O Tools/UIProbe/frame-window.swift -o tmp/uiprobe/frame-window-orig
Tools/UIProbe/frame-window.swift:110:36: error: cannot call value of non-function type 'SCWindow?'
Tools/UIProbe/frame-window.swift:128:45: error: cannot infer contextual base in reference to member 'screen'
Tools/UIProbe/frame-window.swift:73:32: error: value of type 'CMSampleBuffer' has no member 'presentationTimingTime'
Tools/UIProbe/frame-window.swift:103:9: error: binary operator '+' cannot be applied to operands of type 'String' and 'String.Stride'
```

110 那条是 `owningPID` 不存在引起的**级联错**（闭包类型检查失败后 `first(where:)` 退化成了 `first` 属性）。

改法（全部有编译器或运行时判据，不是抄文档）：

| 症状 | 改法 | 判据 |
|---|---|---|
| `SCWindow` 无 `owningPID` | 用 `w.owningApplication?.processID`，选窗**按面积取最大** | 见 §1.3 原样输出（同 pid 有 1920x30 一类窄窗） |
| `CMSampleBuffer.presentationTimingTime` 不存在 | 用 C 访问器 `CMSampleBufferGetPresentationTimeStamp(_:)` + `CMTimeGetSeconds`；`timescale=0` 时它给 NaN，用 `isFinite` 判有效 | 编译通过并解出 pts（`p95_on_pts_axis_ms` 与宿主轴逐位一致） |
| `SCStreamOutputType.screen` 推断不出 | 写全 `SCStreamOutputType.screen`（`addStreamOutput` 在本 SDK 有两个**同名**重载，同步那个返回 `()`） | 编译器原话：`cannot convert value of type '()' to expected argument type 'Bool'` |
| `String + String.Stride` | 拆成 `let` 语句再拼 | 编译通过 |
| **（草稿没报、但最贵的一条）** 回调一帧都不来 | 见 §1.2 | 运行时 selector 判据 |

### 1.2 `SCStreamOutput` 回调名写错 = 静默零帧（这一条值回票价）

头文件里该方法是 `@optional`：

```objc
// SCStream.h:537-545（本机 SDK）
@protocol SCStreamOutput <NSObject>
@optional
- (void)stream:(SCStream *)stream didOutputSampleBuffer:(CMSampleBufferRef)sampleBuffer ofType:(SCStreamOutputType)type;
```

Swift 侧的可见名字**不是** `stream(_:didOutput:ofType:)`。运行时判据（`tmp/frames/selector-probe.swift` 原样输出）：

```
C(didOutput:of:)          : init
D(didOutputSampleBuffer:of:): init | stream:didOutputSampleBuffer:ofType:
responds C to stream:didOutputSampleBuffer:ofType: = false
responds D to stream:didOutputSampleBuffer:ofType: = true
```

⇒ 只有 `func stream(_ aStream: SCStream, didOutputSampleBuffer sampleBuffer: CMSampleBuffer, of type: SCStreamOutputType)`
才把 selector 暴露成框架要调的那个。草稿用的 `didOutput … ofType:` 编得过、**一帧都不给**
（第一次实测就是 `presented_n=0 buffers_n=0`，而窗口确实在动，见 §1.3 的截图判据）。
所以现在工具里带运行时自检并把它打出来：

```
callback_bound=true
delegate_bound=true
content_basis=pixel_signature
```

`callback_bound=false` 时工具直接 `exit 3` 并把 `presented_n` 写成 `n/a`——
**「仪器坏了」和「窗口静止」必须能分开**，否则 0 帧会被读成「卡住」或「零掉帧」。

### 1.4 【最重要】到达节奏 ≠ 内容变化：三发正对照

校准目标 `tmp/frames/control-window.swift`（**临时产物，不进仓库**）：一个我自己起的 AppKit 窗口，
`Timer` 按 `--hz` 重画一根移动的条，`--stall-ms` 可以在主线程注入**已知长度**的停顿。
它不是 AIObservatory，不碰任何车道正在跑的实例。

**第一发（口径错的那版）**：按「PTS 推进」去重，目标窗口 60 Hz 重画 + 每 2 s 注入 500 ms 主线程停顿：

```
presented_n=920  presented_p50_ms=16.593  presented_p95_ms=19.278  presented_max_ms=30.049
dup_n=0  pts_advanced_frames_n=920
```

⇒ **500 ms 的已知停顿完全看不见**（max 只有 30 ms）。每个样本的 presentationTimeStamp 都在推进，
所以「SCStream 只为内容变化出帧 + 用 PTS 去重」这条组合是**错的**：
它量的是采集管道的送帧节奏，不是 App 的出画面节奏。
同一目标再退一档更明显——窗口每秒只重画 1 次（`--hz 1`）时，旧口径照样报 `presented_n=796 / 10 s`。

**第二发（口径改成「画面像素真的变了」）**：判据两路——SCK 的 `SCStreamFrameInfo.dirtyRects` +
自算的 16×32 网格像素 FNV 签名。同一目标 `--hz 1`：

```
presented_n=15   presented_p50_ms=992.524  presented_p95_ms=1008.396  presented_max_ms=1008.396
buffers_n=763    dup_n=748
dirty_change_frames_n=0   dirty_unknown_frames_n=763      ← 见下
content_basis=pixel_signature
```

⇒ 15 次内容变化 / 10 s ≈ 每秒 1 次，**与真实重画次数一致**；`dup_n=748` 就是管道自己送的重复帧。
顺带一条实测：**本机窗口过滤器根本不给 `dirtyRects` 键**（`dirty_unknown_frames_n` = 全部样本），
所以脏矩形这条路不可用，只能自己比像素。签名漏检的方向是「把有变化看成没变化」⇒ 只会低估帧数，
不会虚报流畅，是安全方向。

**第三发（已知停顿必须被看见）**：`--hz 60 --stall-every 120 --stall-ms 500`：

```
presented_n=792  presented_p50_ms=16.696  presented_p95_ms=32.593  presented_max_ms=533.970
hitch_gt2_n=76
CSV top8 间隔: [36.4, 476.7, 516.4, 517.4, 517.5, 519.3, 531.6, 534.0]
```

⇒ 每一发 500 ms 停顿都在 CSV 里留下一个 ≈517 ms 的坑。**这仪器能看见掉帧**，
前提是帧的定义取「像素变了」而不是「样本到了」。

### 1.5 按窗口通道的分辨率下限 ≈ 60 内容帧/s（这把尺子量不到 120 Hz）

同一个正对照窗口，`--hz 120 --speed 0.35`（控制侧自报 `control ticks=2159` / 18 s = 120 次重画/s，
且 `--speed` 保证相邻帧像素不同），同一时刻分别用两种过滤器采：

```
=== 窗口过滤器 ===                      === 显示器过滤器（整屏，--display）===
presented_n=772                          presented_n=1059
presented_p50_ms=16.501                  presented_p50_ms=9.411
presented_p95_ms=18.119                  presented_p95_ms=17.452
buffers_n=785                            buffers_n=1119
                                         vsync_ms=8.333  vsync_n=1435
```

⇒ 源确实在 >100 次/s 改像素（整屏通道看得见），**窗口通道却封顶在 ≈60 内容帧/s（P50 16.5 ms）**。
所以：

* `p95_presented_ms ≤ vsync_ms × 1.05`（= 8.75 ms）在 120 Hz 屏上**永远不可能由窗口通道满足**——
  这不是 App 的锅，是尺子的下限。**F1 用它判 = 不可判**（不是 fail，是 n/a）。
* 它能判的是劣化：P50 明显 > 16.7、或 max 出现几十/几百 ms 的坑（§1.4 第三发已证明灵敏度）。
* 整屏通道分辨率更高但会把别的窗口/光标的变化混进来 ⇒ 只能当「有东西在动」的粗筛，不能归因到某个窗口。

### 1.6 静止窗口 0 帧怎么读（同是 pid 21500，三次读数差 8 倍）

只读观测另一条车道的实例（不启动、不 kill、不点它），三次：

```
（17:27，12 s）presented_n=0    buffers_n=0     callback_bound=true      ← 那一刻画面真的没变
（18:19，30 s）presented_n=41   p50=16.543 p95=57.221 max=951.998  hitch_n=26
（18:20，12 s）presented_n=105  hitch_n=104     buffers_n=762 dup_n=657
```

⇒ 同一个 pid 的读数在几分钟内从 0 跳到 105/12 s，**因为它的内容由别的车道的操作决定**。
所以：`presented_n=0` + `callback_bound=true` = 「这一窗没有新内容」，合法读数，**不是卡住**；
而 21500 的任何读数都**不能当基线**（基线必须是 A2 自己起、自己驱动交互的那个 pid）。

### 1.7 与仪器一的同窗对照（两把尺子差多少）

同窗并跑（`probe-vsync --seconds 32` 与 `frame-window --pid 21500 --seconds 30`；
当窗 `load averages: 12.13 12.53 12.90`，`swift-frontend=0`）：

| 量 | 仪器一（进程内 CVDisplayLink） | 仪器二（frame-window 内嵌 CVDisplayLink） | 差 |
|---|---|---|---|
| vsync P50 | `8.333 ms`（n=3850 / 32 s = 120.3 Hz） | `vsync_ms=8.333`（`vsync_n=3593` / 30.02 s = 119.7 Hz） | **0.000 ms** |
| vsync 抖动 | videoTime `min=P95=P99=max=8.333`；hostTime `P95=9.026 max=9.336` | `vsync_host_p50_ms=8.333` | 同量级 |
| CADisplayLink（进程内第二个通道） | `P50=8.333 max=25.602`（走主 runloop） | — | 消费端抖动，不是显示端跳拍 |
| 该窗口的呈现间隔 | **量不到**（进程内不知道自己有没有出画面） | `P50=16.543 P95=57.221 max=951.998` | 见下 |

⇒ 两把尺子对**显示端节拍**逐位一致（8.333 ms，120 Hz 成立，一帧没跳）。
分歧全部在**消费端**：仪器二报的 16.5 ms 里混着它自己的 ≈60 Hz 下限（§1.5），
所以现在**不能**把「P50=16.543」读成「App 只跑 60 fps」——这个数在两把尺子之间**不可归因**。
这正是「两种独立仪器互验才允许下构成类结论」的活例：这次互验的结论是
**「显示端 120 Hz 成立 + 外部窗口通道不足以判 120 fps」**，而不是「App 掉到 60 fps」。

## 2. 仪器三 `turn-trace.sh`（进程外主线程 turn / hang 取证）

### 2.1 (a) 档可用：`xcrun xctrace record --template 'Animation Hitches'` 非 root、无开发者模式

```

  == xcrun xctrace record --template 'Animation Hitches' --attach 60497 --time-limit 20s --no-prompt ==
  rc=0 墙钟 120s（录 20s ⇒ ≈6× 目标窗口，会压满 CPU）
  ✅ 录到 turn-60497-Animation-Hitches-20260920-181546.trace（1.1G）
turn_n=799
turn_p50_ms=16.664
turn_p95_ms=17.426
turn_p99_ms=136.454
turn_max_ms=137.679
turn_gt_100ms_n=8
hang_events_n=8
hang_types=Brief Unresponsiveness:8
hitches_n=149        hitches_max_ms=125.000
frame_lifetime_n=930 frame_lifetime_p50_ms=17.660 frame_lifetime_max_ms=140.840
hang_risks_n=0
```

另一次更早的同型运行（目标 20 s、注入 12 次 120 ms 停顿，`load` 相对低）：

```
turn_n=1209  turn_p50_ms=16.665  turn_p95_ms=18.056  turn_p99_ms=20.465  turn_max_ms=318.017
turn_gt_100ms_n=12

```

⇒ **注入 12 次 120 ms 主线程停顿 ⇒ `turn_gt_100ms_n=12`，一条不多一条不少**；
`turn_p50=16.665` 正是 60 Hz 心跳。这条通道对 F4 是**可用的**，不是 n/a。

可导出的表（`--toc` 里与本机相关的部分，原样）：

```
<table schema="hitches"/>                       （实测 109 行，带 narrative-description）
<table hangs-threshold="33" schema="potential-hangs" target-pid="SINGLE"/>
<table schema="hang-risks" detect-priority-inversions="0" target-pid="SINGLE"/>
<table schema="hitches-frame-lifetimes"/>  <table schema="hitches-gpu"/>  <table schema="hitches-framewait"/>
<table schema="runloop-events" target-pid="SINGLE"/>
<table schema="display-compositor-interval" target-pid="SINGLE"/>
```

导出只有一个坑（前人已踩过，记着）：`--xpath` 必须是完整路径且属性值用双引号；
写成 `--schema X` 或 `--xpath '<table schema="X"/>'` 会让 xctrace 抛
`-[NSXMLElement traceNodeKind]: unrecognized selector` 并留下 0 字节文件。

### 2.2 两处**静默假阴性**（上一版留下的，这一版已修，写下来免得再长回来）

1. `hang_events_n` 取的是 `hang-risks` 表 —— 在**确实有 13 条挂起**的那一窗里 `hang-risks` 是
   **0 行**（见上面 `hang_risks_n=0` 与 `hang_events_n=13` 同时成立）。照它下 F4 结论会把
   「有 hang」读成「零 hang = 达标」。真数在 `potential-hangs`（表头自带 `hangs-threshold="33"`）。
2. 解帧寿命用了 `<duration units="...">` 正则 —— 本机导出**没有 `units=` 属性**：
   实形是 `<duration id="2" fmt="16.11 ms">16108875</duration>`。
   原样验证：`带 units= 的 duration 出现次数: 0`、`负责人脚本的正则命中数: 0`（983/1683 行全落空）
   ⇒ `turn_n=0` 会被当成「量到零」，而真相是解析没命中。现在优先读 `fmt=`，退到纳秒原值。

### 2.3 口径与三条必须记住的解释

* `turn_*` = **主线程 `CFRunLoop` `individual_iteration` 的 START→END 墙钟差**（真「单次 turn」口径）。
  不是 CPU 采样占比，也不是单帧耗时。
* `frame_lifetime_*` / `hitches_*` = 合成器口径。它们是 turn 的**上界代理**：
  帧寿命 > 100 ms ⇒ 那一拍确实超了；≤ 100 ms **不能**反推主线程没超（一帧可能由多个 turn 拼成）。
  方向不对称 ⇒ 只有「超限」能用它们判。
* **仪器自己会造 hang**：`--attach` 挂上去那一刻目标被冻住。上一版实测第一条
  `hang_max_ms=12472.170`（12.5 s）就是这么来的。所以现在另打
  `hang_earliest_start_ms` 与 `hang_events_ex_first_5000ms_n`，把「App 挂了」和「仪器挂上去那一下」分开。
* **仪器会拖慢被观测方**：同一目标 60 Hz，不挂仪器时 `turn_n=1209`（20 s / 60.4 Hz），
  挂上后 `turn_n=799`（20 s / 40 Hz）⇒ 掉到 ≈2/3。所以 F4 的绝对值只能在**同一次挂载态内**比，
  或在 note 里带这个折扣。

### 2.4 (b) 降档 `System Trace`：也录得出来（同一套表）

```
  == 降档 (b)：--template 'System Trace' ==
```
（脚本在 (a) 失败时自动试一次。两档都失败才落到 (c)。）

### 2.5 (c) `spindump`：**不可用**（本机原样，`sudo -n` 试探，没有弹框、没有猜密码）

```
$ /usr/sbin/spindump 2 1 -stdout
spindump must be run as root when sampling the live system
$ sudo -n true
sudo: a password is required
```

⇒ 这一档在本机拿不到数。**同时留下这条判据给以后的人**：`spindump` 的读数**必须连 Note 一起读**——
`CPU Time: 1.064s / Duration: 120s` 看着像 0.88% 很省，但同段
`Note: process was unresponsive for 119 seconds before sampling` 才是真相（主线程约 91% 忙且挂起）。
只看 CPU 百分比会把「挂死」读成「很闲」。

### 2.6 旁证 `sample`：可用（非 root），但它不是 F4 的尺子

```
$ sample 61302 3 -file tmp/frames/sample-busy.txt     # 我自己起的 yes > /dev/null
Sort by top of stack, same collapsed (when >= 5):
        write  (in libsystem_kernel.dylib)        2556
$ sample 61371 3 -file tmp/frames/sample-idle.txt     # 我自己起的 sleep 40
Sort by top of stack, same collapsed (when >= 5):
        __semwait_signal  (in libsystem_kernel.dylib)        2675
```

⇒ 「忙 vs 等」可判（这正是当年性能页自旋用过的口径）。但**必须显式给 `-file`**：
不给时它会写到 `/tmp`（AGENTS §0 的越界落点）。且它会 attach ⇒ 只许在取证轮跑，禁入帧判据窗口。

### 2.7 代价（写判据时必须带上）

| 项 | 实测 |
|---|---|

`frames-tools.contract.md` 的「取证轮口径」段与 `frame-baseline.schema.md` 的「待落列」注，

| `turn-trace.sh 因此不提供实现`、`turn_* 一律填 n/a`、**F4 在本机降为不可判** | 模板 `Animation Hitches` 非 root 可用（§2.1，两次 rc=0、真数与注入停顿逐条对上）⇒ **F4 有外部通道** |

## 4. 未覆盖条件（这些我**没**测到，别当成已验）

1. **没在产品实例上跑过 `turn-trace.sh`**：不许对别的车道的 21500 做 attach（会冻它），
   而 A2 自己起的 pid 我没有授权时点。⇒ 对产品二进制（SwiftUI + 真页面）的 turn/hang 读数尚未取得。
2. **没测遮挡语义**：正对照与 21500 的窗口当时都在屏幕上（`onScreen`）。
   完全被遮挡 / 最小化 / 换 Space 的窗口，SCStream 是否还出帧——未知。
   （§1.6 的 0 帧读数不能用来回答这条。）
3. **120 fps 的窗口通道正对照没做出来**：不是没试（`--hz 120 --speed 0.35`，控制侧自报 120 tick/s），
   而是窗口通道自己封顶 ≈60（§1.5）。⇒ 「真 120 fps 的 App 在窗口通道上会长什么样」仍是外推。
4. **切页（`switch`）交互下的 hitch 形态没测**：需要产品侧配合驱动切页，A2 独占启动权。
5. **`hitches` 表的 109 行 vs `potential-hangs` 的 13 行没有建立换算关系**：

6. **F5（`phys_footprint`）不属本探针范围**：由 A1 的 `probe-footprint` 负责，这里只引用契约口径。
7. 高负载窗（load ≥ 15）下的所有绝对值都只报了差值：本轮 §1.7 与 §2.1 的 `load1` 分别是
   12.13 与 17.73——后者**不能**当绝对判据。
